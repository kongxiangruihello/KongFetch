# KongFetchCore

KongFetch 的搜索引擎核心库，不依赖 AppKit，可独立编译和测试。这是"下一版"第一阶段的成果，应用界面尚未接入。

## 内容

| 模块 | 作用 |
| --- | --- |
| `NameIndex` | 名称索引。列式存储：所有名称存放在同一块字节数组中，父目录、类型、折叠后的检索键、扩展名边界、拼音都是并行数组，搜索时多核扫描，不为每个文件创建对象。 |
| `ExclusionRules` | 可配置的排除规则。默认只按精确路径排除 `~/Library`，名称排除仅限 `node_modules`、`.git`、`DerivedData`、`.Trash`；用户自己命名为 `build`、`Library` 的文件夹会被收录（3.2 会漏掉）。 |
| `NameIndex.apply` | 增量更新。每个变动只重读其所在文件夹并比对，耗时取决于涉及的文件夹，而不是索引大小。 |
| `FileChangeWatcher` | FSEvents 监听，可从保存的事件 ID 续接：应用未运行期间的改动会在下次启动时补上，不必整盘重扫。 |
| `NameIndex.save/load` | 二进制索引文件，按列整块读写，替代 3.2 的 JSON 路径数组。 |
| `SearchSession` | 边输入边搜索。新查询只是在旧查询后追加字符或词时，只在上次结果中重新打分。 |
| `KongFetchLegacy32` | 3.2 匹配与扫描代码的原样副本，仅用作测试和基准的对照。 |

## 与 3.2 的一致性

三种精度（精确名称、模糊名称、名称及路径）的打分与 3.2 逐项一致，由 `MatchingParityTests` 对每个文件、每条查询逐一比对验证。

## 测试与基准（需在 Mac 上运行）

```sh
cd Core
swift test                                  # 全部测试
swift run -c release kfbench synth /tmp/tree 300000
swift run -c release kfbench new /tmp/tree     # 新引擎
swift run -c release kfbench legacy /tmp/tree  # 3.2 对照
```

`scripts/mac-test.sh test|bench|all` 在 Mac 上编译、测试或运行基准，输出写入 `Core/.logs/`（脚本不联网，代码需另行同步）。

## 首轮实测（2026-10-27）

环境：Apple 芯片 Mac，macOS 27.0.1，Swift 6.4，release 编译。合成目录树共 300,450 个文件、25,299 个文件夹；对比时两边使用相同的排除规则（3.2 规则），收录条目同为 220,358 个。

| 项目 | 3.2 | 新引擎 |
| --- | --- | --- |
| 建立索引 | 4,846 ms | 7,525 ms |
| 索引常驻内存 | 431 MB | 86 MB |
| 索引文件大小 | 36.2 MB（JSON） | 20.0 MB（二进制） |
| 保存索引 | 659 ms | 15.5 ms |
| 载入索引 | 1,349 ms | 29.8 ms |
| 单次查询（模糊名称，12 条查询） | 5.9–7.6 秒 | 0.6–2.7 ms |
| 单次查询（名称及路径，12 条查询） | 2.4–9.8 秒 | 0.8–4.4 ms |
| 逐字输入 "contract"（7 次查询） | 55.8 秒 | 3.7 ms（收窄）/ 7.7 ms（不收窄） |

- 两边 24 组查询的命中数完全相同；`MatchingParityTests` 另对 1,500 余个文件的每个分数逐一比对，结果一致。
- 3.2 一栏只计打分循环（单线程），不含 3.2 应用为每个结果读取文件属性的开销，因此对 3.2 偏有利；它的 NSCache 上限为 5 万条，少于条目数，缓存会被反复冲掉，这与大目录下的实际情况相符。
- 新引擎建立索引较慢，原因是建索引时预先计算了全部文件名的折叠形式和拼音（3.2 推迟到查询时才算）。配合 FSEvents 断点续接，整盘重建只在首次或事件历史失效时发生。并行读取目录是下一步的优化方向。
- 使用新的默认排除规则时收录 315,494 个条目，多出的 95,136 个位于名为 `build`、`Library` 的用户文件夹中（3.2 会跳过）。这个差额取决于合成树的构造，只说明规则差异，不代表真实磁盘上的比例。
